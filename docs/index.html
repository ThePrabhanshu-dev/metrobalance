The problem

Riders cannot see their balance without touching a machine

“No, you cannot check your card balance online.” — DMRC Smart Card FAQ (dmrcsmartcard.com)
  • To know “how much is left”, a rider must find an Add Value Machine or a staffed counter.
  • Top-ups stay invisible until a gate rejects the journey — the fare deduction is the only feedback.
  • Students, senior citizens, tourists and daily commuters cannot reconcile top-ups against journeys themselves.
  • Every such query becomes staff time at a counter or a call-centre interaction.

The proposal

One public enquiry surface for every Smart Card

MetroBalance turns card enquiries into a self-service web experience — and is architected so that DMRC can plug in an authorised data source later without rewriting a single line of the UI.

Consumer

Balance in one tap

Type the card number, read the available balance in rupees and the timestamp of the last update. No registration, no OTP, no app install.

Consumer

Full statement

Recharge history with amount, channel and mode — and every journey fare deduction with stations, line and fare slab, so a rider can reconcile their card themselves.

DMRC-facing

Ready for an authorised feed

A single IMetroCardProvider seam isolates the data source. Swap the demo provider for an authorised DMRC service and every screen keeps working.

What we are not asking for

No exclusive rights, no paid licence, no per-transaction fee, no hardware, no change to the card, no new app for riders to install, and no data scraped from any website.

The DMRC seam

IMetroCardProvider is the only door to card data. Today it is served by an in-memory demo provider.

When an authorised feed is granted, we implement the same interface, register it in the DI container and switch one configuration flag — no controller, view or service changes.

Deliberate design choices

  • No database — in-memory lists & dictionaries; nothing to breach.
  • No scraping — nothing is read from any DMRC or third-party site.
  • No invented data — every response is flagged as demo or real.
  • No paid dependencies — .NET 10, Bootstrap 5, Swagger. All free.

Uniform envelope: { success, message, data, errorCode, timestampUtc } · HTTP 400 invalid card, 404 unknown card, 409 blocked or expired card.

Contract stability

These endpoints and their JSON shape are the integration contract. An authorised DMRC service can be added behind them, so any consumer written against this API keeps working unchanged.

White-label ready

The front end can be re-skinned to DMRC branding and embedded on the official website as a self-service widget — subject to DMRC's branding approval.

MetroBalance7
Trust & compliance

Privacy and safety are designed in, not bolted on

No card data stored

The current build holds no card data at all. A production build would be stateless per request.

No personal data

Only the card number typed by the rider is processed — no name, no phone number, no OTP, no account.

No scraping

We never read or replicate data from DMRC, partner or any other website.

Transparent labelling

Every response states whether it is demo or live, and a real card never carries a fabricated amount.

Proposed controls for a DMRC production deployment

  • Request rate-limiting and per-IP throttling on the enquiry endpoints
  • TLS-only, HSTS, standard security headers and a strict Content-Security-Policy
  • Anti-forgery tokens on form posts and an audit trail of enquiry requests
  • No card identifiers in logs; truncation and hashing where retention is required
  • Data-minimisation aligned with the Digital Personal Data Protection Act, 2023
  • DMRC-hosted or DMRC-approved hosting, with an agreed retention and deletion policy

How we integrate

Four paths to live data — we need only one

Preferred

A · Authorised read API

DMRC (or its nominated processor) exposes a read-only balance & transaction endpoint over mTLS or signed requests. MetroBalance becomes a pure consumer. Highest control, cleanest audit trail.

Low effort

B · Settlement / ledger feed

DMRC's back-office already records top-ups and fare deductions. A nightly or near-real-time export of that ledger lets the service answer “what was left” without touching the card or the station network.

Zero backend

C · AVM / kiosk deep link

A rider taps a QR code or NFC tag at the machine; the browser reads the balance the machine already displays and the app simply renders it. No backend integration at all.

Launch now

D · Guided self-service

From day one, DMRC's own FAQ channels are surfaced inside the app: AVM locations, counter guidance and recharge instructions in the rider's language, with no live data required.

Options A and B are server-side and fit the existing architecture exactly. Options C and D ship value immediately while A is being formalised. We are happy to start with D and pilot A.

Honesty first

What we will never do

  • Never scrape DMRC, dmrcsmartcard.com or any partner site to build a balance figure.
  • Never invent a balance, a transaction or an endpoint and present it as real.
  • Never bypass card security, station systems or DMRC access controls.
  • Never lock riders in — no login wall, no app install, no data held about users.
  • Never use DMRC branding or the DMRC name without written permission.
The application is honest by default: for a real card it shows DMRC's published position and the official channels — because that is the truth today. — This is also why the architecture is ready for an authorised feed the day DMRC grants one.

Governance

  • DMRC approves branding, wording and placement before anything goes live.
  • Written agreement on data scope, retention and audit before the feed is enabled.
  • DMRC can require the service to be hosted inside its own environment.
  • Public disclosure that the service is a third-party initiative where DMRC wishes.
